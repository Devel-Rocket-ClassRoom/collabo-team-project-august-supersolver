## 1. 설계의 전제가 되는 확정 사항

| # | 결정 | 근거 |
|---|---|---|
| 1 | 그리기는 시뮬레이션 **시작 전에만** 가능. 일시정지는 관찰 전용(그리기 잠금) | 미션 가이드의 위상 분리("그리기를 마친 뒤 시작 버튼") + 일시정지가 배속과 함께 관찰 기능으로 묶여 있음. 시뮬 중 그리기를 허용하면 솔루션에 시간 축이 생겨 탐색·난이도·리플레이 전부가 질적으로 어려워짐 → 3개월 MVP에 부적합. **팀 확정** — 기획서에 명시 |
| 2 | 솔루션 = **시간 축 없는 정적 스트로크 집합** | 결정 1의 귀결. 탐색 공간에서 "언제" 차원이 제거됨 |
| 3 | 솔버와 게임은 **동일한 코드 경로**를 사용 | 잉크 파이프라인(단순화→콜라이더)과 시뮬 스텝 코드가 하나여야 "솔버 통과 = 유저도 클리어 가능"이 성립 |
| 4 | 솔버의 판정은 **하한 증명** | 제한된 프리미티브 어휘로 풀리면 자유 곡선을 쓰는 사람은 당연히 풀 수 있음. 어휘의 한계로 인한 오류는 항상 안전한 방향(풀리는데 못 찾음)이며, 거짓 양성(안 풀리는데 풀린다고 판정)은 구조적으로 없음 |
| 5 | **역방향 변환(Stroke → θ)은 범위에서 제외** | 파이프라인의 어떤 필수 단계도 요구하지 않음. 프리미티브는 Generate() 단방향 함수만 가짐. 피팅·웜스타트·스트로크 인식 UX 전부 미구현 |
| 6 | 리플레이는 **물리에 투입된 최종 스트로크**를 저장 | θ나 단순화 전 원본을 저장하면 상류 파이프라인(전개 함수, 단순화 알고리즘) 변경 시 재현이 깨짐 |
| 7 | 렌더링도 **물리와 동일한 단순화 스트로크**를 사용 | 크레용 감성은 원본 궤적 보존이 아니라 셰이더 등 표현 계층에서 처리. 물리·표시·저장이 단일 데이터로 통일되어 리플레이 스키마가 단순해짐 |
| 8 | 솔버 시뮬 시간 상한 **30초(1,800스텝)** | 좋은 풀이는 10~20초 내 클리어. 30초 초과 풀이만 존재하는 레벨은 세션 기준(30초~2분) 밖이라 반려가 정당 |
| 9 | 프리미티브 초기 어휘는 **바퀴 포함 7종** | 회전축 도구가 초기 콘텐츠에 포함되므로 솔버 어휘도 동시 지원 |

## 2. 결정론 (최우선 해결 과제)

### 2.1 규칙

- 물리는 오직 `PhysicsScene2D.Simulate(FixedDt)` 수동 호출로만 전진. `FixedDt = 1/60` 고정
- **dt는 절대 변경 금지.** 가속은 dt를 키우는 것이 아니라 초당 호출 횟수를 늘리는 것 (dt 변경 = 물리 결과 변경 = 검증 무효)
- 시뮬 로직(바람·폭탄·스위치)은 전부 **스텝 카운트 기반**. `Time.time`, `deltaTime`, 코루틴 `WaitForSeconds`, `Time.timeScale` 사용 금지
- 난수는 주입된 `System.Random(seed)` 단일 인스턴스만 사용. `UnityEngine.Random` 접근 금지
- **오브젝트 생성·등록 순서 고정**: 장치는 레벨 데이터 순서, 스트로크는 리스트 순서로 인스턴스화 (Box2D는 바디 등록 순서에 민감)
- 되돌리기/초기화/재시도는 상태 되감기가 아니라 **월드 전파괴 → 재구축**
- 솔버 월드에서 오브젝트 풀링 금지 (풀 반납 순서가 다음 시도의 생성 순서를 오염시켜 결정론 파괴). 시도마다 파괴·재생성하며, 생성 비용은 시뮬 비용 대비 무시 가능
- Physics2D 잡 옵션(스텝 내부 멀티스레딩) 사용 금지 — 부동소수점 합산 순서 변동으로 결정론 파괴 위험

### 2.2 플랫폼 간 리스크와 대응

솔버는 에디터(x64), 게임은 실기기(ARM64)에서 실행되며 부동소수점 연산의 비트 단위 동일성은 보장되지 않는다. 대응: 솔버가 찾은 대표 풀이 리플레이를 실기기에서 재생해 같은 결과가 나오는지 **표본 검증**하는 절차를 QA에 포함한다. 이는 발표 자료(결정론 시연)로도 사용한다.

### 2.3 결정론 자동 테스트 (코어 완성의 정의)

같은 (level, solution, seed) 2회 실행 → 스텝별 월드 상태 해시 비교. 이 테스트의 통과가 코어 완성 조건이며, 이후 CI처럼 주기적으로 실행해 팀원의 결정론 오염을 즉시 검출한다.

## 3. 코어 아키텍처

### 3.1 계층 구조

```
[순수 C# — 프레임/렌더링 무지]
SimWorld        한 판의 시뮬 상태 전체. Step()이 유일한 시간 전진 수단
WorldBuilder    LevelData + Solution → 격리 씬에 월드 구축 (등록 순서 고정)
Judge           클리어/실패/정지 판정 + MinGoalDist 계측

[MonoBehaviour — 얇은 드라이버]
GameSimDriver   게임 플레이용. 누적기 패턴으로 실시간 전진 (배속·일시정지 보유)
SolverRunner    솔버용. 프레임 예산 또는 무제한 전진
```

- 격리 물리 씬: `SceneManager.CreateScene(..., LocalPhysicsMode.Physics2D)`. 게임 플레이도 동일한 격리 씬 사용 (게임·솔버 실행 환경 통일)
- 시작 전 "그리기 단계"에서는 SimWorld를 생성하지 않음. 상태 머신은 "편집 중(월드 없음) ↔ 시뮬 중(월드 있음)" 2상태
- 계약 타입 + 시뮬 실행부는 별도 asmdef로 분리하고 UI·렌더링 참조를 차단 ("코어는 프레임을 모른다"를 컴파일 에러로 강제)

### 3.2 핵심 타입

```csharp
// ── 계약 타입 (전원 공유) ──
public enum ToolType { FixedLine, FreeBody }

public struct Stroke
{
    public ToolType Tool;
    public List<Vector2> Points;      // 단순화 후 포인트. 물리·렌더링·저장이 이 하나를 공유
}

public struct PivotJoint              // 회전축: 포인트가 아니라 연결 정보
{
    public int StrokeA, StrokeB;
    public Vector2 Anchor;
}

public class Solution                 // "한 판의 그림 전체"
{
    public List<Stroke> Strokes;
    public List<PivotJoint> Pivots;
    public float TotalInk();
}

public enum SimOutcome { Clear, Fail, Stalled, Timeout }

public readonly struct SimResult
{
    public readonly SimOutcome Outcome;
    public readonly int EndStep;      // 클리어 시간
    public readonly int Stars;
    public readonly float InkUsed;
    public readonly float MinGoalDist; // 시뮬 전체에서 공-목표 최소 거리. CEM 점수 재료
}
```

- `SimOutcome.Stalled`(전 바디 sleep + 대기 타이머 없음)를 별도 상태로 두는 것이 조기 종료의 핵심 — 실패 시도 대부분이 수 초 내 결판나 솔버 처리량을 좌우
- `MinGoalDist`는 모든 Outcome에 포함. 전부 실패인 탐색 초반에도 "어느 후보가 그나마 나은지" 학습 신호 제공

```csharp
// ── 시뮬 실행부 ──
public class SimWorld
{
    public const float FixedDt = 1f / 60f;
    public int CurrentStep { get; private set; }
    public Judge Judge { get; }

    public void Step()   // 로직 → 물리 → 판정 순서 박제
    {
        foreach (var l in _logics) l.Tick(CurrentStep, _rng);
        _physics.Simulate(FixedDt);
        Judge.Evaluate(CurrentStep, this);
        CurrentStep++;
    }
    public bool IsTerminal => Judge.Cleared || Judge.Failed || Judge.Stalled;
}

public interface IStepLogic           // 장치 6종의 계약 = 결정론 강제 장치
{
    void Tick(int step, System.Random rng);   // deltaTime이 시그니처에 없음
    bool HasPendingWork { get; }              // Stalled 판정용 (폭탄: 폭발 전 true 등)
}

public interface IStrokeProcessor     // 잉크 파이프라인 (팀원 B 담당)
{
    Stroke Process(ToolType tool, List<Vector2> rawPoints);  // 시뮬 시작 전에 호출
}

public static class ColliderFactory   // WorldBuilder 내부에서 호출
{
    public static GameObject Create(PhysicsScene2D scene, Stroke s);
}

public static class WorldHasher       // 결정론 테스트·디싱크 디버깅·실기기 검증 공용
{
    public static ulong Hash(SimWorld w);  // 전 바디의 position/rotation/velocity 순서 해시
}
```

### 3.3 게임 드라이버 (누적기 패턴)

```csharp
void Update()
{
    if (_world == null || Paused || _world.IsTerminal) return;
    _accumulator += Time.deltaTime * SpeedMultiplier;
    int safety = 0;
    while (_accumulator >= SimWorld.FixedDt && safety++ < 8)  // 스파이럴 방지
    {
        _world.Step();
        _accumulator -= SimWorld.FixedDt;
    }
}
```

- 프레임레이트(30/60/120)와 무관하게 스텝 수·순서 동일 → "프레임 속도가 결과에 영향 금지" 요구를 구조로 충족
- `SpeedMultiplier` = 배속 기능, `Paused` = 일시정지가 공짜로 도출
- FixedUpdate 미사용 이유: 호출 시점·횟수를 Unity가 관리해 통제 불가. 수동 누적기는 배속·일시정지·솔버 재사용이 같은 코드에서 나오며, "물리를 전진시키는 코드가 프로젝트에 단 하나"가 됨

## 4. 데이터 흐름: 두 파이프라인의 합류

```
유저:  손가락 궤적(원본) ── Process(단순화) ──┐
                                              ├─ Stroke ─→ 시뮬 ─→ SimResult
솔버:  θ 샘플(원본) ── Generate(전개) ────────┘
```

| | 유저 솔루션 | 솔버 솔루션 |
|---|---|---|
| 인과적 원본 | 포인트 배열 | θ (프리미티브 설정값) |
| Stroke의 지위 | 원본 그 자체 | θ의 결정론적 전개 결과 |
| θ의 지위 | 존재하지 않음 | 솔버 내부에만 존재, 시뮬 경계를 넘지 않음 |

시뮬 호스트는 두 출처를 구분하지 않는다. 이 통일이 보장하는 것: 검증의 정당성(같은 코드 경로), 리플레이 포맷·재생기 단일화, 디자이너 참조 풀이 시드의 무변환 주입.

## 5. 프리미티브 (솔버의 후보 생성 어휘)

### 5.1 원리

무작위 포인트 배열 탐색은 불가능 (포인트 20개 = 40차원, 유효 형태의 부분공간이 극도로 얇음). 대신 사람이 그릴 법한 형태를 **저차원 설정값(θ, 3~6차원)으로 파라미터화한 부품**으로 정의하고, 전개 함수 `Generate(anchor, θ) → StrokeSet`으로 스트로크를 생성한다. 어떤 θ에서도 항상 유효한 형태가 나오도록 공간 자체를 접는 것이 핵심.

```csharp
public interface IPrimitive
{
    StrokeSet Generate(Vector2 anchor, float[] theta);  // 단방향만 존재
}
```

### 5.2 초기 어휘 (7종 확정)

| 프리미티브 | θ | 생성물 | 물리적 기능 |
|---|---|---|---|
| 경사면 Ramp | 오프셋(x,y), 각도, 길이 | 고정선 | 방향 전환 |
| 발판 Platform | 오프셋, 길이 | 수평 고정선 | 받침, 다리 |
| 벽 Blocker | 오프셋, 높이 | 수직 고정선 | 차단, 방향 전환 |
| 상자 Box | 오프셋, 크기 | 닫힌 자유물체 | 밀기, 누르기 |
| 그릇 Bowl | 오프셋, 폭, 깊이 | 포물선 고정선 | 받아 멈추기 |
| 지렛대 Lever | 받침 오프셋, 판 길이, 각도 | 고정선+자유물체+회전축 세트 | 기계적 증폭 |
| 바퀴 Wheel | 오프셋, 반지름 | 원형 자유물체+중심 회전축 | 구름 |

- 회전축은 단독 유전자가 아님 — 복합 프리미티브(지렛대·바퀴) 내부에 캡슐화하여 항상 유효한 구성만 생성
- 생성된 스트로크는 게임과 동일한 잉크 파이프라인을 통과 (같은 코드 경로 원칙)
- θ의 위치는 앵커 기준 **상대 오프셋** — 앵커가 달라져도 지식이 재사용됨

### 5.3 어휘 크기에 대한 판단

6~8종이면 충분하며 확대는 오히려 해롭다:
1. 솔버의 임무는 "모든 풀이"가 아니라 "풀이 하나"(하한 증명)
2. 이 장르 풀이의 물리적 기능은 여섯 동사(받친다·꺾는다·잇는다·민다·받는다·증폭한다)로 포화. 잉크 제한이 최적해를 단순 형태로 누름
3. 표현력은 종류가 아니라 조합에서 나옴 (8종 × 앵커 ~15개 × k≤3 = 수만 구조 조합 × 연속 변주)
4. 어휘가 크면 같은 예산에서 부품당 시도가 줄어 수렴 실패 — 어휘 크기는 표현력 vs 탐색 효율의 트레이드오프

**어휘 확장 프로세스** (상상이 아니라 실측 실패 데이터로만 성장):
- 솔버 실패 → 디자이너가 직접 풀어봄 → 디자이너도 실패 = 레벨 반려 (솔버가 제 역할)
- 디자이너만 성공 = 그 풀이 형태가 새 부품 후보 (전개 함수 하나 추가)
- 엘리트 풀이에 한 번도 등장하지 않는 부품은 제거
- 즉시 안전망: 디자이너 참조 풀이를 시드로 주입 (스트로크 포인트 직접 섭동 — 역변환 불필요)
- 리포트에 "탐색 실패 레벨 + 커버리지"를 누적해 "어휘 몇 종이면 충분한가"를 데이터로 답변

## 6. 솔버 파이프라인 (3단계)

솔버는 서로 다른 두 질문 — "풀리는가?"(존재 증명)와 "얼마나 어려운가?"(난이도) — 를 분리해 답한다. 최적화 탐색의 성공률을 난이도로 쓰면 탐색이 똑똑할수록 모든 레벨이 쉬워 보이는 왜곡이 생기기 때문.

### 6.0 0단계 — 빈 해 검사

빈 솔루션(아무것도 안 그림)을 먼저 시뮬. 안 그려도 풀리는 레벨은 퍼즐로서 반려. 부산물로 얻는 공의 실패 궤적은 1단계의 prior가 된다 (§6.1.3).

### 6.1 1단계 — 풀이 탐색 (CEM)

#### 6.1.1 솔루션 게놈

```
Solution = [ Gene₁ ... Geneₖ ]   (k = 0~3, 잉크 제한 내)
Gene     = (프리미티브 종류 c, 앵커 인덱스 a, 연속 파라미터 θ)
```

앵커: 공 시작점·목표·별·장치 주변에 미리 샘플링한 "부품을 놓을 만한 자리 목록". 탐색 공간을 화면 전체가 아닌 의미 있는 지점으로 좁힌다.

#### 6.1.2 탐색 절차 (CEM = "잘 된 후보 주변을 더 파본다")

1. 세대당 N=100개 후보를 현재 분포에서 샘플링해 전부 시뮬 → 적합도 산출
2. 상위 10%(엘리트)의 경향으로 분포 갱신
3. 다음 세대는 갱신된 분포에서 샘플링 — 반복하며 수렴
4. 클리어 발견 후에도 예산 내 계속 탐색 → 서로 다른 풀이 수집

혼합 공간(이산 c·a + 연속 θ)이므로 분포를 계층으로 관리:
- **이산부**: (종류×앵커) 확률 테이블 `P[c][a]`를 엘리트 등장 빈도로 갱신. 확률 하한(1~2%) 유지로 조기 붕괴(국소해 고착) 방지
- **연속부**: 조합별 가우시안 `N(μ[c][a], σ[c][a])`을 그 조합을 쓴 엘리트의 θ로 갱신. 조합별 분리 이유: "목표 옆 경사면은 30도"와 "시작점 발판은 수평"은 다른 지식
- **개수 k**: 분포로 관리, 초기값은 적은 개수 선호 `P(k)=0.05/0.5/0.3/0.15` (잉크 페널티상 단순한 해가 좋은 해 + 저차원일수록 수렴 빠름)
- 잉크 초과 시 리샘플링이 아니라 **길이 축소로 예산에 맞춤** (리샘플링은 긴 부품을 분포에서 밀어내는 편향 유발)

#### 6.1.3 첫 세대 prior — 빈 해 궤적 활용

0단계 실패 궤적을 읽어 첫 세대를 "실패를 고치는 방향"으로 편향:
- 공이 떨어져 죽는 지점 → 그 아래/직전 앵커에 발판·경사면 prior ↑
- 궤적이 목표에 근접했다 멀어지는 지점 → 경사면·벽 prior ↑
- 궤적-목표 사이 공백 → 다리(발판) prior ↑
- 공이 안 움직이는 레벨 → 공 뒤 앵커에 상자·지렛대 prior ↑
- 경사면 초기 각도 분포 = 목표 방향 중심의 넓은 가우시안

#### 6.1.4 적합도 함수

```
f = -min_t dist(ball_t, goal)     ← SimResult.MinGoalDist
    + 클리어 보너스(대) + 별 보너스
    - 잉크 페널티(소) - 시간 페널티(소)
```

#### 6.1.5 판정과 예산

- **단계적 예산 구조 확정**: 1차(소) — 클리어 시 즉시 종료 → 2차(중) → 3차(대) → 소진 시 판정. 각 단계의 회차 **수치는 벤치마크 실측 후 확정**하며, 코드에는 튜닝 가능한 설정값으로 구현 (예시 초기값: 300 / +700 / +1,000)
- 총 예산 소진까지 클리어 없음 → **"풀이 불가 의심" 플래그** (요구사항: 풀리지 않는 레벨 필터링)
- 한계 인지: 게놈은 유전자 간 독립 가정 — 조합 의존성("A는 B가 있을 때만 의미")은 직접 표현 불가하나 엘리트 갱신이 좋은 조합을 통째로 살려 간접 학습됨. MVP 범위(k≤3)에서 충분하며, 부족 시 GA 하이브리드로 확장 (설계 문서에 한계와 확장 경로 명시)

#### 6.1.6 풀이 다양성

성공 솔루션을 (프리미티브 종류 조합 + 위치 그리드 양자화) 시그니처로 클러스터링 → "서로 다른 풀이 개수" 산출. 요구사항 "의도 밖 풀이를 솔버가 찾아내 보여줄 것"의 직접 구현이자 발표 핵심 데모.

### 6.2 2단계 — 난이도 측정 (탐색과 분리)

| 지표 | 방법 | 측정 대상 |
|---|---|---|
| 발상 난이도 SolveRate_random | 앵커 기반 무작위 배치 M회 성공률 (M은 벤치마크 후 확정, 예시 초기값 300) | "아무렇게나 그려도 되는가" |
| 실행 난이도 Robustness | 1단계 성공 솔루션에 위치·각도·길이 가우시안 노이즈(σ 2~3단계) 주입 후 성공률 | "정답을 알아도 손이 삐끗하면 실패하는가" — 모바일 터치 체감 난이도와 최고 상관 |

**2지표 분류 구조는 확정.** 아래 기준값은 코드에 const로 입력하는 **예시 초기값**이며, 담당자(솔버)가 초반 레벨 플레이테스트로 직접 캘리브레이션해 확정한다:

| 등급 | 무작위 성공률 (예시) | 관용도 (예시) |
|---|---|---|
| 쉬움 | ≥ 5% | ≥ 60% |
| 보통 | 1~5% | ≥ 40% |
| 어려움 | < 1% | ≥ 20% |
| 반려 | 탐색 실패, **또는** 관용도 < 하한(예시 10% — 이론상 풀리나 사람이 못 그리는 정밀도) | |

관용도 하한을 반려 조건에 넣는 구조가 핵심 — 성공률만으로는 "풀리지만 사람은 못 푸는" 레벨을 못 거른다. 하한 수치 역시 const 예시값으로 시작해 테스트로 확정.

확장 아이디어: 노이즈 σ를 실제 사람 터치 오차 분포(플레이테스트 실측)로 캘리브레이션하면 "사람 기준 난이도"라는 근거를 확보 — 솔버 설계 문서에 명시할 어필 포인트.

## 7. 리플레이

### 7.1 포맷

```json
{
  "levelId": "L017",
  "seed": 42,
  "gameVersion": "0.3.1",
  "strokes": [ { "tool": "FixedLine", "points": [[1.2, 3.4]] } ],
  "pivots":  [ { "a": 0, "b": 1, "anchor": [2.0, 1.5] } ],
  "solverMeta": { "genes": [] }
}
```

- **strokes = 물리에 투입된 최종 형태** (유저: 단순화 후 / 솔버: Generate 전개 후). 재생 시 상류 파이프라인을 재실행하지 않으므로 알고리즘 버전 변경으로부터 재현이 격리됨
- `seed` 필수: 스트로크가 같아도 시뮬 중 난수(폭탄 파편 등)가 다르면 결과가 다름. 스트로크+시드+버전 3종 세트가 결정론 재현의 완성
- `gameVersion`: 물리 파라미터 변경 빌드에서의 재생 결과 차이를 "버그"와 "정상적 버전 불일치"로 구분 (불일치 시 경고 표시)
- `solverMeta.genes`(θ): 재생에는 미사용, 분석·클러스터링 재계산용 메타데이터로만 보관 (재현 데이터와 분석 데이터의 분리)
- 렌더링도 단순화 스트로크를 사용하므로(결정 7) `visualPoints`는 존재하지 않음 — 물리 재현과 시각 재현이 같은 데이터로 일치하며, 크레용 감성은 셰이더에서 처리
- 유저/솔버 리플레이가 같은 스키마·같은 재생기 하나를 사용

### 7.2 용도

플레이 기록 재생(요구사항), 결정론 검증 수단(실기기 표본 검증, §2.2), 발표 자료(솔버 베스트 풀이 재생).

## 8. 헤드리스 실행과 성능

### 8.1 실행 형태 3종

| 모드 | 용도 | 방식 |
|---|---|---|
| 에디터 타임슬라이스 (기본) | 발표 즉석 시연, 제작 중 단건 검증 | 코루틴에서 프레임당 ~33ms 예산만큼 Step 후 yield. 진행률 UI 표시 |
| 배치모드 CLI | 야간 전수/회귀 검증 | `Unity -batchmode -executeMethod SolverCLI.Run` → 결과 JSON |
| (공통) 격리 물리 씬 | 메인 씬 오염 방지, 게임과 환경 통일 | `LocalPhysicsMode.Physics2D` |

### 8.2 가속의 원리

- 배속 = (1/60초) ÷ 스텝당 실측 비용. dt는 불변, 호출 횟수만 증가
- 스텝당 0.1~0.3ms는 2D 소규모 씬의 예상치(벤치마크 실측 대상) → 자연 배속 50~166배 수준 기대
- 시뮬 시간 상한 **30초(1,800스텝) 확정** (결정 8)

### 8.3 소요 시간 추정

- 아래 수치는 전부 벤치마크 실측 전의 추정치. 33분/레벨(2,000회 × 1초)은 최악 상한이며, 조기 종료·수렴·단계적 예산 반영 시 현실 기대값은 **~500회 × ~0.3초 ≈ 2~3분/레벨** 수준
- 발표 즉석 시연 모드: 1차 예산 + 축소 표본만으로 "풀림/안 풀림 + 대략 난이도"를 빠르게 산출 (예시 구성으로 ~90초). 정밀 리포트는 야간 배치
- **헤드리스 호스트 완성 즉시 벤치마크 실측** (스텝당 시간, 시도당 평균, Stalled 비율) — 예산·상한 파라미터를 추정이 아닌 측정으로 결정

### 8.4 병렬화

- **스레드 병렬 불가**: `Simulate()` 포함 Unity API는 메인 스레드 전용. Physics2D 잡 옵션은 결정론 위험, 별도 C# 물리엔진은 "같은 코드 경로" 원칙 위반으로 배제
- **프로세스 병렬 가능**: 배치모드 인스턴스 다중 실행 + 작업 JSON 분배 + 결과 병합. 같은 바이너리·같은 플랫폼이면 프로세스 간 결정론 유지
- 병렬 단위는 **레벨 간**만 (완전 독립). CEM은 세대 간 순서 의존이 있어 레벨 내부 분산은 비효율 — 레벨 하나 = 프로세스 하나
- 우선순위: MVP 필수 아님. 40레벨 직렬로도 현실적 시간. 배치 CLI를 만들어두면 병렬화는 셸 스크립트 수준의 확장

## 9. 팀 인터페이스 계약 (첫 2주 내 코드로 확정)

| 계약 | 당사자 | 내용 |
|---|---|---|
| Stroke / Solution / PivotJoint | 본인 ↔ B | 솔버 출력이자 잉크 파이프라인 출력, 리플레이 본체 |
| SimResult + 실행기 시그니처 | 본인 (코어 소유) | `Run(level, sol, seed, maxSteps) → SimResult`. 조기 종료·MinGoalDist 계측 포함 |
| LevelData JSON | C ↔ 전원 | 앵커 생성 원료(시작점·목표·별·장치 위치)와 잉크 제한이 기계가 읽기 좋은 형태로 포함될 것 |
| IStepLogic | 본인 ↔ B | 장치 6종의 결정론 강제 계약 (step + 주입 rng만 제공) |
| 리플레이 스키마 | 본인 ↔ D | 자동 저장 시스템과 공유 |

역할 분담: 본인 = 결정론 코어 + 결정론 테스트 + 시뮬 호스트 + 솔버·프리미티브·리플레이 (크리티컬 패스). B = 잉크 파이프라인 + 장치 6종. C = LevelData·에디터·해금·레벨 디자인 리드. D = 조작 UI·튜토리얼·자동 저장·빌드·스토어.

## 10. 구현 순서 (리스크 순)

1. **결정론 코어 + 계약 확정** (1~2주차 최우선, 솔버 착수 금지): SimWorld·WorldBuilder·Judge·계약 타입 + 결정론 자동 테스트 초록불. 목표는 "공 하나 굴러가는 최소 코어"지 완성품이 아님. 이후 코어 동결 (변경 시 결정론 테스트 + 리뷰 필수)
2. **헤드리스 호스트 + 조기 종료** → 즉시 벤치마크 실측
3. **프리미티브 + 무작위 탐색만으로 엔드투엔드** — 이 시점에 "솔버가 레벨을 판정한다" 데모 성립. 팀 첫 마일스톤(6주차 목표): 코어 + C의 목표 장치 + D의 그리기 UI + 무작위 탐색으로 레벨 1개 판정
4. **CEM 업그레이드** (무작위 탐색 위의 개선 — 일정이 밀려도 코어 데모는 유지됨)
5. **난이도 2지표 + 분류**
6. **다양성 클러스터링 + 리포트/엑셀 export**
