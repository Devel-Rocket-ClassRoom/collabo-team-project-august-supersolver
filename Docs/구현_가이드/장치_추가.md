## 2. 계약

```csharp
public interface IStepLogic
{
    void Tick(int step, System.Random rng);
    bool HasPendingWork { get; }
}
```

시그니처가 곧 강제 장치다. **경과 시간이 인자에 없고, 난수는 주어진 것만 쓸 수 있다.**
그 밖의 방법으로 시간이나 난수를 끌어오려면 계약을 어겨야 하고, 그 순간 자동 검사에 걸린다.

### `Tick(step, rng)`

- **시간은 `step` 으로만 센다.** 60 스텝 = 1초. "3초 뒤"는 `step >= _armedStep + 180`
- **난수는 인자 `rng` 만.** `UnityEngine.Random` 은 코어에서 금지이며 테스트가 소스를 읽어 잡아낸다
- 물리가 진행되기 **전에** 불린다. 스텝 순서는 `로직 → 물리 → 판정` 으로 박제되어 있다

### `HasPendingWork`

조기 종료 판정용이다. **아직 할 일이 남아 있으면 `true`.**

전 바디가 잠들었는데 이 값이 전부 `false` 면 코어가 `Stalled` 로 판정하고 시뮬을 끊는다.
폭탄이 폭발을 기다리는 중인데 `false` 를 돌려주면 **터지기 전에 잘려나간다.**

반대로 영원히 `true` 를 돌려주면 그 레벨은 절대 `Stalled` 가 안 나고 매번 상한(1800스텝)까지 간다.
솔버가 레벨 하나에 수백~수천 번 시도하므로 이건 처리량에 직결된다.
**할 일이 끝나면 반드시 `false` 로 내릴 것.**

## 3. 결정론 규칙 네 가지

`BombDevice` 에 전부 들어 있다. 새 장치도 같은 규칙을 지켜야 한다.

### ① 난수는 `Tick` 안에서만 뽑는다

```csharp
if (_fireStep < 0)
    _fireStep = _data.DelaySteps + rng.Next(_data.JitterSteps);
```

생성자에서 뽑으면 안 된다. `rng` 는 계약상 `Tick` 에서만 주어지며,
그래야 난수 소비 순서가 **"스텝 순서 × 장치 등록 순서"** 로 고정된다.
월드 구축 중에 뽑으면 구축 순서까지 난수 순서에 얽혀 보장할 것이 한 겹 늘어난다.

### ② 바디는 등록 순서대로 순회한다

```csharp
for (int i = 0; i < _bodies.Count; i++) { ... }
```

순서를 바꾸거나(정렬, 거리순 등) 병렬로 돌리면 힘이 가해지는 순서가 바뀌고,
부동소수점 합산 순서가 달라져 **같은 입력이 다른 결과를 낸다.**

### ③ 힘보다 속도를 직접 더하는 편이 안전하다

```csharp
body.linearVelocity += direction * power;
```

`AddForce` 는 질량으로 나뉘는데, 자유 물체의 질량은 길이에서 나온 임시값이다.
그 상수가 조정되면 장치 세기가 같이 흔들린다.

### ④ 잠든 바디는 명시적으로 깨운다

```csharp
body.WakeUp();
```

**Physics2D 는 3D 와 다르다.** 잠든 바디에 힘을 줘도 스스로 깨지 않는다.
이걸 빠뜨리면 "발동했는데 아무 일도 안 일어나는" 장치가 된다.

## 4. 바디를 갖는 장치

**장치는 콜라이더를 가져도 된다.** 장애물이나 문처럼 물리적 실체가 있는 장치는 바디가 필요하다.
폭탄·바람 구역처럼 영역 효과만 있는 것이 안 가질 뿐이다.

만드는 방법은 `BombDevice.CreateBody` 를 보면 된다. 요점은 둘이다.

**① 팩토리에서 만들고, 만든 즉시 `bodies` 에 넣는다**

```csharp
case DeviceType.Obstacle:
{
    var body = ObstacleDevice.CreateBody(scene, data, $"Device_{index}");
    bodies.Add(body);
    return new ObstacleDevice(data, body, bodies);
}
```

등록 순서를 정하는 것은 장치가 아니라 팩토리다. 월드의 고정 순서에서
**장치는 지형 뒤·스트로크 앞**이며, 거기가 "레벨이 만드는 것"과 "유저가 그리는 것"의 경계다.

`bodies` 에 넣지 않으면 해시에도 `Stalled` 판정에도 잡히지 않아, 보이는데 없는 물체가 된다.

**② 컴포넌트 순서를 지킨다**

`transform.position` 을 먼저 놓고 `Rigidbody2D` 를 나중에 붙인다.
`autoSyncTransforms` 가 꺼져 있어서 나중에 transform 을 옮겨도 바디는 따라오지 않는다.

## 5. 바디를 없애는 장치 (문, 소모품)

문이 열리는 것도, 폭탄이 소모되는 것도 결국 **바디 제거**다.

```csharp
UnityEngine.Object.DestroyImmediate(_body.gameObject);
_body = null;
```

### `Destroy` 가 아니라 `DestroyImmediate` 여야 한다

`Destroy` 는 프레임 끝까지 지연된다. 그런데 **한 프레임에 도는 스텝 수는 바깥 사정이다** —
게임에서는 누적기가 0~8 번, 솔버에서는 1800 번을 한 프레임에 몰아 돌린다.
지연 파괴를 쓰면 바디가 실제로 사라지는 스텝이 프레임 경계에 따라 달라져
**프레임 독립성이 그 자리에서 깨진다.**

`Tick` 은 물리 콜백 밖이고 물리 스텝 사이의 지점이라 즉시 파괴가 안전하다.

### 목록에서 빼지 않는다

파괴해도 `bodies` 리스트에서 제거하지 않는다. 빼면 뒤 인덱스가 전부 밀려
해시 구조가 통째로 바뀐다. 코어의 해시는 **null 자리를 그대로 섞도록** 되어 있다 —
"여기 뭔가 있었다"는 사실 자체가 디싱크 신호이기 때문이다.

리스트 항목이 null 이 될 수 있으므로, 바디를 순회하는 코드는 **항상 null 검사**를 해야 한다.

## 6. 파라미터 싣기

지금 스키마는 이렇다. **placeholder 이므로 바꿔도 된다.**

```csharp
[Serializable]
public struct DeviceData
{
    public DeviceType Type;
    public Vector2 Position;
    public float Radius;       // 영향 반경
    public float Power;
    public int DelaySteps;
    public int JitterSteps;    // rng 로 뽑는 추가 지연
}
```

종류가 늘면 공용 필드 하나로는 감당이 안 될 것이다. 종류별 파라미터 블록으로 나누는 게 나을 수 있다.
바꿀 때 지킬 것은 셋뿐이다.

- `JsonUtility` 가 다룰 수 있는 형태 — **public 필드 + `[Serializable]`, 다형 직렬화 불가**
- `LevelData.Devices` 의 **리스트 순서 = 등록 순서 = 난수 소비 순서**
- `DeviceType` enum 값은 뒤에만 추가

`LevelData` 는 팀 공유 계약이라 **바꾸기 전에 알릴 것.**

## 7. 확인하는 방법

### 최소 테스트

`Assets/_Project/Tests/PlayMode/DeviceTests.cs` 가 폭탄으로 무엇을 검사하는지 보고 같은 것을 만들면 된다.

- 레벨 데이터에서 로직으로 등록되는가
- 대기 중일 때 전 바디가 잠들어도 `Stalled` 가 아닌가
- 발동하면 실제로 뭔가 움직이는가
- 반경 밖은 안 건드리는가
- (바디가 있다면) 파괴 시점이 프레임 분할에 영향받지 않는가

마지막 것이 특히 중요하다. `Destroy` 를 쓰면 **거기서만** 걸린다.

### 눈으로

`SimScrubber` 를 씬의 아무 GameObject 에 붙이면 슬라이더로 스텝을 넘기며 볼 수 있다.
장치 위치와 영향 반경이 원으로 그려지고, 대기 중이면 보라색·전부 발동하면 마젠타로 바뀐다.

### 결정론 재검증

**장치를 추가하면 결정론 테스트를 다시 돌린다.** PlayMode 탭이다 — EditMode 만 초록불인 것은
아무것도 검증하지 않은 것과 같다. 시드를 바꿔 결과가 달라지는지도 함께 본다
(`rng` 를 쓰는 장치라면 달라져야 정상이다).

## 8. 하지 말 것

| | 이유 |
|---|---|
| `Time.deltaTime` / `Time.time` | 코어 금지. 자동 검사가 소스에서 잡아낸다 |
| `UnityEngine.Random` | 같은 이유. 주입된 `rng` 만 쓴다 |
| `FixedUpdate` / 코루틴 대기 | 호출 시점을 Unity 가 관리해 통제할 수 없다 |
| 생성자에서 난수 뽑기 | 난수 소비 순서가 월드 구축 순서에 얽힌다 |
| `Object.Destroy` | 지연 파괴 → 프레임 독립성 붕괴 |
| 파괴한 바디를 목록에서 제거 | 뒤 인덱스가 밀려 해시가 통째로 바뀐다 |
| `HasPendingWork` 를 계속 `true` | `Stalled` 가 영영 안 나고 솔버 처리량이 무너진다 |
| 물리 콜백(`OnCollisionEnter2D` 등)으로 판정 | 호출 순서·시점을 물리 엔진이 정한다. 매 스텝 직접 계산할 것 |
