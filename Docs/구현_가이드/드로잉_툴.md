# 드로잉 툴 구현 가이드

> **근거** — [팀_인터페이스_계약](../팀_인터페이스_계약.md) · **실제 코드** `Core/Contracts/` (`Stroke` · `Solution` · `PivotJoint` · `IStrokeProcessor`) · `Core/Sim/WorldBuilder.CreatePivot`
> **이 문서가 바뀌면** — 함께 볼 하위 문서는 없다 (말단)
> **회전축 동작이나 `ColliderFactory` 의 두께·질량 처리가 바뀌면 이 문서를 고쳐야 한다** — §4·§6 이 그 동작을 그대로 설명하고 있다
> 전체 관계: [문서 지도](../README.md)

**만드는 것**: 손가락 궤적을 받아 물리에 넣을 `Stroke` 로 만들고, 한 판의 `Solution` 을 조립해
시뮬을 시작시키는 것까지.

**산출물**: `IStrokeProcessor` 구현체 + 입력·UI 코드. 코어는 손대지 않는다.

---

## 1. 전체 흐름

```
손가락 궤적 (raw points)
      ↓  IStrokeProcessor.Process()      ← 여기가 당신이 만드는 것
   Stroke (단순화 끝난 최종 포인트)
      ↓  Solution.Strokes 에 추가
   Solution
      ↓  GameSimDriver.StartSimulation(level, solution, seed)
   시뮬 시작
```

**`Process()` 가 돌려준 포인트가 물리·렌더링·리플레이 저장에 전부 그대로 쓰인다.**
표시용 원본을 따로 남기지 않는다 — `visualPoints` 같은 필드는 만들지 않는다(설계서 결정 7).
크레용 같은 질감은 셰이더에서 낸다. 물리와 화면이 다른 선을 쓰는 순간
"보이는 대로 부딪힌다"가 깨지고 유저가 억울해진다.

## 2. 계약

```csharp
public enum ToolType
{
    FixedLine,   // 그린 자리에 붙박이로 남는 발판 (정적 바디)
    FreeBody,    // 중력을 받아 떨어지는 물체 (동적 바디)
}

public struct Stroke
{
    public ToolType Tool;
    public List<Vector2> Points;   // 월드 좌표, 최소 2개. 폴리라인이면 몇 개든 좋다
    public float Length();         // 잉크 소모량 = 선분 길이의 합
    public bool IsValid { get; }   // Points 가 2개 이상인가
}

public struct PivotJoint
{
    public int StrokeA, StrokeB;   // Solution.Strokes 의 인덱스. -1(WorldIndex) = 월드 고정
    public Vector2 Anchor;         // 회전 중심, 월드 좌표
}

public class Solution
{
    public List<Stroke> Strokes;
    public List<PivotJoint> Pivots;
    public float TotalInk();       // 회전축은 잉크를 쓰지 않는다
    public Solution Clone();
}
```

당신이 구현할 인터페이스는 하나다.

```csharp
public interface IStrokeProcessor
{
    Stroke Process(ToolType tool, List<Vector2> rawPoints);
}
```

**결정론 부담이 없다.** 이 함수는 시뮬 시작 전에만 불린다 — 그리기는 시뮬 중에 잠기기 때문이다.
`Time`, `UnityEngine.Random`, 코루틴 뭘 써도 된다. 코어 안에서만 금지다.

유효한 선을 만들 수 없으면(너무 짧다 등) `IsValid == false` 인 값을 돌려주면 호출부가 버린다.
예외를 던질 필요 없다.

## 3. 실무

### 스트로크 만들기

```csharp
Stroke stroke = _processor.Process(currentTool, rawPoints);
if (!stroke.IsValid) return;                       // 너무 짧은 선 등

if (solution.TotalInk() + stroke.Length() > level.InkLimit) return;   // 잉크 초과

solution.Strokes.Add(stroke);
```

**잉크 제한은 코어가 강제하지 않는다.** `LevelData.InkLimit` 은 데이터일 뿐이고,
넘겨도 `WorldBuilder` 는 그냥 만든다. 막는 것은 UI 쪽 일이다.

### 회전축 붙이기

`PivotJoint` 는 스트로크가 아니라 **연결 정보**다. 잉크를 쓰지 않는다.

```csharp
public struct PivotJoint { public int StrokeA, StrokeB; public Vector2 Anchor; }
```

두 인덱스는 `Solution.Strokes` 기준이고, `-1`(`PivotJoint.WorldIndex`) 은 "스트로크가 아니라 월드"를 뜻한다.
**어느 쪽에 `-1` 을 넣든 결과는 같다** — 코어는 두 인덱스를 대칭으로 다룬다.

#### 두 형태

**① 스트로크 ↔ 스트로크** — 두 물체를 한 점에 붙이고, 그 점을 중심으로 **상대 회전만** 허용한다.
서로 떨어지지 않는다.

```csharp
solution.Pivots.Add(new PivotJoint(2, 5, anchor));
```

한쪽이 `FixedLine`(정적)이면 그쪽은 움직이지 않으므로, 결과적으로 **동적 물체가 그 점에 매달린다.**
받침대에 얹은 지렛대, 기둥에 매단 간판이 이 형태다.
둘 다 `FreeBody` 면 **둘 다 움직이면서** 그 점에서만 이어져 있다 — 집게, 이중 진자.

**② 스트로크 ↔ 월드** — 스트로크를 **화면의 절대 좌표에 못박는다.**

```csharp
solution.Pivots.Add(new PivotJoint(3, PivotJoint.WorldIndex, anchor));
```

①에서 정적 스트로크에 매다는 것과 물리적 효과는 같지만, **못이 보이지 않고 잉크를 쓰지 않는다.**
받침대를 그리지 않고도 축을 세울 수 있다는 뜻이다.
바퀴의 중심축, 눈에 보이는 기둥이 필요 없는 지렛대 받침이 여기 해당한다.

> UI 설계는 B 의 판단이다. 예를 들어 "탭한 점 위에 스트로크가 둘이면 ①, 하나면 ②"처럼
> 자동으로 고를 수도 있고, 도구를 나눌 수도 있다. 코어는 어느 쪽이든 받는다.

#### 이어 붙이면 사슬이 된다

같은 스트로크를 여러 축이 잡아도 된다. `(A,B)` 와 `(B,C)` 를 넣으면 A–B–C 가 이어진
**사슬**이 되고, 크레인 팔이나 이중 진자 같은 것이 만들어진다.
한 스트로크에 조인트가 여러 개 붙는 것도 문제없다.

다만 물리 쪽 사정이 있다.

- **사슬이 길수록 축이 늘어져 보이고 떨린다.** Box2D 는 구속을 반복 근사로 푸는데,
  마디가 늘어날수록 한 스텝 안에 오차가 다 흡수되지 않는다. 3~4 마디까지가 안전하다
- **닫힌 고리는 피할 것.** `(A,B) (B,C) (C,A)` 처럼 순환을 만들면 구속이 서로 모순되어
  솔버가 진동한다. 결과가 재현은 되지만(결정론은 유지된다) 물리가 지저분해진다
- 잉크 제한이 사슬 길이를 자연히 눌러 주므로, 보통은 UI 에서 따로 막지 않아도 된다

`Pivots` 리스트 순서도 조인트 생성 순서이자 물리 해결 순서다. **순서를 뒤섞지 말 것.**

#### 한 스트로크에 축을 둘 박으면 — 회전이 죽는다

2D 강체의 자유도는 셋(x, y, 회전)이고 힌지 하나가 그중 **둘**(앵커점의 병진)을 없앤다.
하나 박으면 회전 하나가 남고, **다른 점에 하나 더 박으면 그 회전도 사라진다** —
축 1 을 중심으로 돌면 축 2 의 앵커가 움직여 버리기 때문이다.

| 두 축이 잡는 대상 | 결과 |
|---|---|
| 둘 다 **월드** | 그 자리에 **완전히 고정**된다. 위치도 회전도 잠긴다 |
| 둘 다 **같은 상대 스트로크** | 두 스트로크가 **한 덩어리로 용접**된다. 덩어리 자체는 움직인다 |
| 하나는 월드, 하나는 다른 자유 물체 | 고정이 아니다. 링크 기구가 된다 (크랭크 같은 것) |

셋 다 정상 입력이고 결정론도 유지된다. 여분 구속이 있어도 반복 순서가 고정되어 있기 때문이다.

다만 **여분 구속**이라는 점은 알아둘 것. 자유도 3 인 물체에 구속식 4 개가 걸리는 셈이라
Box2D 가 두 조인트를 번갈아 밀며 푼다. 보통은 가만히 있지만 외력이 세면 미세하게 떨릴 수 있고,
솔버 일감도 늘어난다.

**"이 선을 고정하고 싶다"가 목적이라면 `FixedLine` 을 그리는 편이 낫다.** 정적 바디라
솔버 비용이 0 이고 떨림도 없다. 축 두 개로 고정하는 것은 "자유 물체를 나중에 못박는" 플레이나
**두 자유 물체를 용접해 ㄱ자 한 덩어리로 만드는** 용도로 의미가 있다 — 그건 막을 이유가 없다.

#### 축 위치는 "무엇을 만들고 싶은가"의 문제다

축이 물체의 무게중심과 겹치는지 여부는 **금지 사항이 아니라 설계 선택**이다.

| 축 위치 | 중력만 있을 때 | 쓰임 |
|---|---|---|
| 무게중심 **위** | 안 돈다 (중립 평형) | 바퀴, 회전문, 팽이 — **부딪힐 때만 돈다** |
| 무게중심에서 **벗어남** | 스스로 회전해 아래로 처진다 | 진자, 지렛대 — 가만히 둬도 기운다 |

지적한 대로 **무게중심에 축이 있어도 물체가 부딪히면 돈다.** 중력 토크만 0 일 뿐이다.
설계서의 바퀴 프리미티브가 정확히 이 경우다(원형 자유물체 + 중심 회전축).
"지렛대처럼 저절로 기울기를 바란다면" 축을 중심에서 벗어나게 두면 된다.

#### 회전축은 물리적 실체가 없다

현재 구현은 기존 스트로크 바디에 `HingeJoint2D` 컴포넌트를 하나 붙일 뿐이다.
**GameObject 도, 콜라이더도, 바디도 만들지 않는다.**

따라서:

- 공이나 다른 물체가 **축에 부딪히지 않는다.** 축은 물체가 아니라 구속 조건이다
- 잉크를 쓰지 않고, 월드의 바디 수도 늘지 않는다
- **화면에 그리려면 별도로 그려야 한다.** `Solution.Pivots[i].Anchor` 좌표를 알고 있으므로
  거기에 표식을 찍으면 된다 (`SimScrubber` 가 그렇게 한다)

콜라이더를 주지 않는 것이 맞다고 본다. 조인트가 이미 위치를 구속하므로 물리적으로 불필요하고,
축을 별도 바디로 만들면 **매달린 물체가 자기 축과 충돌해 조인트와 싸우게 된다.**
"못에 다른 물체가 걸리는" 연출이 필요해지면 그때 코어와 상의할 일이다.

또한 현재는 **자유 회전만** 지원한다. 모터도 각도 제한도 설정하지 않는다.

#### 함정 셋

**한쪽은 반드시 `FreeBody` 여야 한다.** 조인트는 동적 바디에 붙는다.
정적끼리 이으면 붙일 곳이 없어 **조용히 무시된다** — 예외도 로그도 없다.

**잘못된 인덱스는 조용히 "월드 고정"이 된다.** 이게 제일 위험하다.
범위를 벗어난 인덱스는 `-1` 과 똑같이 "월드"로 해석되므로,
`PivotJoint(0, 99, anchor)` 는 오류가 아니라 **스트로크 0 을 허공에 못박는 축**이 된다.

**스트로크를 지우면 뒤 인덱스가 전부 밀린다.** 그래서 위 함정과 겹치면 최악이다 —
스트로크 하나를 지웠을 뿐인데 어떤 축은 엉뚱한 스트로크를 잡고, 어떤 축은 소리 없이
허공 못이 된다. 삭제·되돌리기를 지원한다면 **피벗 인덱스 보정을 반드시 함께** 구현할 것.

### 시뮬 시작

```csharp
_driver.StartSimulation(level, solution, seed);   // GameSimDriver (MonoBehaviour)
```

`GameSimDriver` 가 이미 있다. 하는 일은 경과 시간을 누적기에 넘기는 것뿐이다.

```csharp
_driver.HasWorld          // 편집 중인가 시뮬 중인가
_driver.IsSimulating      // 시뮬 중이고 아직 판정 전인가
_driver.Paused            // 일시정지 (관찰 전용 — 그리기는 계속 잠긴 상태)
_driver.SpeedMultiplier   // 배속
_driver.Stop();           // 초기화·재시도
_driver.Result(inkUsed);  // 결과 — 시뮬이 끝난 뒤에 부를 것
```

## 4. 상태는 두 개뿐이다

```
편집 중 (월드 없음)  ←→  시뮬 중 (월드 있음)
```

- **그리기는 편집 중에만.** 시뮬이 시작되면 잠근다. 솔루션에 시간 축이 없는 것이 이 규칙의 근거다
- **일시정지는 관찰 전용.** 멈춘 상태에서 선을 추가할 수 있게 하면 "시간 축 없는 솔루션"이 깨진다

### 편집 중 되돌리기 — 마음대로 해도 된다

Play 전에는 `SimWorld` 가 아예 없다. **되돌릴 물리 상태가 존재하지 않는다.**
`Solution` 은 그냥 데이터이므로 커맨드 스택이든 스냅샷이든 편한 방식으로 구현하면 되고,
Play 버튼을 누르는 시점에 최종 `Solution` 만 넘기면 그만이다.

다만 **결과물의 모양**에는 두 가지가 걸린다. 되돌리기 방식과 무관하게 지켜야 한다.

- `Strokes` **리스트 순서** — 같은 스트로크 집합이라도 순서가 다르면 물리 결과가 다르다.
  되돌리기·다시하기가 순서를 뒤바꾸지만 않으면 된다
- `Pivots` 의 **인덱스** — 중간 스트로크를 지우는 되돌리기라면 뒤 인덱스가 밀려
  회전축이 엉뚱한 스트로크를 가리킨다

### 시뮬 시작 후 재시도 — 여기는 전파괴다

월드가 생긴 뒤 "다시 시도"는 **`Stop()` 후 다시 `StartSimulation()`** 이다.
바디 위치와 속도를 초기값으로 되돌리는 방식은 안 된다 — 접촉 상태·슬립 상태 같은
물리 엔진 내부 상태는 그렇게 복구되지 않아 두 번째 시도가 첫 번째와 다른 결과를 낸다.

전파괴 후 재구축은 **같은 결과를 정확히 재현한다.** 코어의 결정론 테스트가 그것을 보장하므로
재시도 비용을 걱정할 필요는 없다.

## 5. 알아두면 좋은 물리 쪽 사정

당신이 코드를 쓸 일은 없지만 **결과가 이상해 보일 때 원인**이 되는 것들이다.

- `FixedLine` 은 정적 바디, `FreeBody` 는 동적 바디가 된다
- **`FreeBody` 는 두께가 있다.** 두께 0 인 선끼리는 Box2D 가 충돌을 만들지 않아서,
  동적 스트로크만 반 두께 `ColliderFactory.FreeBodyHalfWidth`(0.06) 만큼 부풀린 다각형이 된다.
  화면에 그리는 선과 실제 충돌 경계 사이에 그만큼 차이가 난다
- **질량은 길이에 비례한다** (`FreeBodyMassPerUnit`). 긴 선일수록 무겁다
- 닫힌 형태(첫 점 = 끝 점)를 그리면 **속이 빈 껍데기**가 된다. 벽은 통과 못 하지만 내부는 비어 있다
- 같은 형태를 몇 점으로 그리든 무게중심·관성은 같게 계산된다. 단순화가 촘촘하든 성기든 물리는 안 흔들린다

## 6. 하지 말 것

| | 이유 |
|---|---|
| 표시용 포인트를 따로 보관 | 물리와 화면이 갈라진다 (설계서 결정 7) |
| 시뮬 중 그리기 허용 | 솔루션에 시간 축이 생겨 솔버·리플레이가 무너진다 |
| `Stroke` → 파라미터 역변환 | 설계 범위 밖이다 (결정 5). 프리미티브는 생성 단방향뿐 |
| 스트로크 삭제 후 피벗 인덱스 방치 | 회전축이 엉뚱한 스트로크를 가리킨다 |
| **시뮬 시작 후** 재시도를 바디 위치 되돌리기로 구현 | 물리 내부 상태가 복구되지 않아 재현이 깨진다. `Stop()` → `StartSimulation()` (편집 중 되돌리기는 해당 없음) |

---

## 7. 확인하는 방법

만든 `Solution` 은 그대로 시뮬에 넣어볼 수 있다.

```csharp
SimResult result = SimRunner.Run(level, solution, seed: 0);
```

`SimScrubber` 에 자기 솔루션을 넣으면 스텝을 넘기며 눈으로 볼 수 있다.
자유 물체는 실제 콜라이더가 아니라 **그은 선**으로 그려지니, 두께 차이만 감안하면 된다.
