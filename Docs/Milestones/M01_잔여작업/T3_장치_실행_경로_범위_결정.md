## 현재 상태 — 미실행이 아니라 미구현이다

[WorldBuilder.cs:48](../../../Assets/_Project/Scripts/Core/Sim/WorldBuilder.cs:48)을 보면 장치 등록 자리가
**주석으로만** 잡혀 있다.

```
// 3. 장치 — 레벨 데이터 순서. M01 범위에는 아직 없다.
//    팀원 B 의 IStepLogic 구현이 합류하는 자리이며, 여기서도 순서는 레벨 데이터 순서다.
```

`logics` 리스트는 만들어지자마자 비어 있는 채로 `SimWorld`에 넘어간다. 결과적으로:

- `SimWorld.Step()`의 로직 루프가 **0회 반복**한다
- `Judge`의 `HasPendingWork` 분기가 실행되지 않는다 — `Stalled` 판정이 "전 바디 sleep"만으로 결정된다
- `_rng`가 아무에게도 전달되지 않아 **시드가 시뮬 결과에 영향을 줄 수 없다**

마지막 항목이 중요하다. 원래 체크리스트가 요구했던 "시드 3개 × 솔루션 3종 = 9조합"은
지금 코어에서 **같은 시뮬을 3번 도는 것**이다. 조합 수는 늘지만 증명되는 것은 늘지 않는다.

그리고 이것들은 "테스트가 안 짜인 경로"가 아니라 **"아직 만들지 않은 기능"** 이다.
없는 기능은 테스트할 수 없다.

## 갈래

### 갈래 A — 범위에서 빼고 재실행 조건으로 이관 (권장)

장치 등록 경로를 M01 동결 범위 밖으로 **명시**하고, 동결 선언문에 다음을 못박는다.

> 장치(`IStepLogic`) 등록 경로는 동결 범위에 포함되지 않는다.
> B의 첫 장치가 합류하는 시점에 `WorldBuilder`의 장치 등록 코드를 추가하며,
> 그때 A-1 매트릭스에 **장치 포함 케이스와 시드 축(3개)** 을 추가하고 결정론 테스트 전체를 재실행한다.
> 이 재실행 통과 전까지 장치를 쓰는 레벨은 솔버 판정 대상이 아니다.

**근거:**

- M01 문서 §3.2가 장치를 이미 명시적 범위 밖으로 선언했다. 체크리스트가 그것과 어긋나 있었을 뿐이다
- 등록 경로를 지금 만들려면 `LevelData`에 장치 목록 필드가 필요하다. `LevelData`는 **팀원 C와 공유된 계약**이고, 장치 스키마는 C의 레벨 에디터와 B의 장치 6종이 함께 정해야 할 것이다. 코어가 혼자 정해서 넣으면 양쪽이 다시 뜯는다
- 동결 직전에 공유 계약을 넓히는 것은 동결의 취지에 정면으로 반한다. 동결은 "더 이상 안 흔든다"는 선언인데 그 직전에 흔드는 셈이다
- 얻는 것은 빈 루프 한 줄의 커버리지다. 치르는 값에 비해 작다

**비용:** 장치가 합류하는 시점에 결정론 재검증 라운드가 한 번 더 필요하다. 이것은 어차피 필요한 작업이다 —
B의 장치는 코드가 새로 들어오는 것이므로, 등록 경로가 지금 있든 없든 그때 다시 돌려야 한다.

### 갈래 B — 지금 구현하고 더미 장치로 덮는다

`LevelData`에 장치 목록을 추가하고, `WorldBuilder`가 그것을 읽어 `IStepLogic`을 만들어 등록한다.
테스트 픽스처에 더미 장치(예: N스텝 뒤 공에 힘을 가하는 가짜 폭탄, 지연 스텝을 `rng`에서 뽑아 시드 반응성 확보)를 둔다.

**얻는 것:** 로직 루프·`HasPendingWork`·시드 축이 전부 동결 전에 검증된다.

**치르는 것:**

- `LevelData` 계약 확장 → **사용자 확인 필수** (CLAUDE.md: 계약 변경은 먼저 확인)
- 장치 스키마를 코어가 선점하게 되고, B·C와 합의 없이 정한 형태가 굳는다
- 더미 장치를 어디에 둘지 문제 — 코어 프로덕션 코드에 넣으면 출하 코드에 테스트 전용 타입이 남고, `PPS.Core.TestFixtures`에 두면 `LevelData`가 테스트 어셈블리의 타입을 참조할 수 없어 팩토리 우회가 필요하다
- M01 범위가 늘어난다. 지금 M01은 이미 실행 검증만 남은 상태다

1차 결정은 "검증 하나 때문에 공유 계약을 넓히지 말자"였고 그건 그것대로 타당했다.
재결정의 차이는 **목적이 검증에서 인수인계로 바뀐 것**이다. 검증만이면 주입 지점으로 충분하지만,
본보기가 되려면 실제로 레벨 데이터에서 나와야 한다 — B가 이어받을 자리가 `DeviceFactory` 의
`switch` 한 줄이라는 게 코드로 보여야 한다.

## 구현 (완료)

### 계약 — `LevelData.Devices`

`JsonUtility` 가 다형 직렬화를 못 하므로 `List<IStepLogic>` 은 불가능하다. 인터페이스로 실으면
JSON 왕복에서 타입이 사라져 "레벨 추가는 데이터만으로"가 깨진다. 그래서 **판별자 + 파라미터** 형태다.

| 추가 | 내용 |
|---|---|
| `DeviceType` | 판별자. 현재 `Bomb` 하나. **값 재배열 금지** — 정수로 직렬화되므로 순서가 바뀌면 기존 레벨·리플레이가 다른 장치를 가리킨다. 추가는 뒤에만 |
| `DeviceData` | `Type` / `Position` / `Radius` / `Power` / `DelaySteps` / `JitterSteps` |
| `LevelData.Devices` | `List<DeviceData>`. **리스트 순서 = 로직 등록 순서 = 난수 소비 순서** |

**이 스키마는 placeholder다.** 장치 6종을 맡은 팀원이 자유롭게 바꿔도 된다 —
종류가 늘면 공용 필드 하나로는 감당이 안 되고, 그때는 종류별 파라미터 블록으로 나누는 편이 낫다.
지키면 되는 것은 둘뿐이다: `JsonUtility` 가 다룰 수 있는 형태일 것, 리스트 순서가 난수 소비 순서라는 것.

### 장치 — `BombDevice`

[Core/Devices/BombDevice.cs](../../../Assets/_Project/Scripts/Core/Devices/BombDevice.cs)

일정 스텝 뒤 터져 반경 안의 동적 바디를 바깥으로 민다. 세기는 가장자리로 갈수록 선형으로 약해진다.

**새 장치를 만들 때 지켜야 할 결정론 규칙이 이 클래스에 다 들어 있다.**

- **발동 스텝을 생성 시점이 아니라 첫 `Tick` 에서 뽑는다.** rng는 계약상 `Tick` 에서만 주어지고, 그래야 난수 소비 순서가 "스텝 순서 × 장치 등록 순서"로 고정된다. 생성 시점에 뽑으면 월드 구축 순서까지 난수 순서에 얽힌다
- **바디를 등록 순서대로 순회한다.** 순서가 바뀌면 힘을 받는 순서가 바뀌고 부동소수점 합산 순서가 달라진다
- **힘이 아니라 속도를 더한다.** 힘은 질량으로 나뉘는데 자유 물체의 질량은 `ColliderFactory` 의 임시값에서 나온다
- **`WakeUp()` 을 명시 호출한다.** Physics2D 는 3D 와 달리 잠든 바디가 힘을 받아도 스스로 깨지 않는다

### 등록 — `DeviceFactory` + `WorldBuilder`

분기를 `DeviceFactory` 로 뺐다. 장치는 계속 늘어나는데 그 변경이 `WorldBuilder` 에 섞이면
"등록 순서가 이 클래스의 존재 이유"라는 계약이 잡음에 묻힌다.
**장치를 추가하는 곳은 `DeviceType` 에 값 하나, `DeviceFactory` 의 switch 에 한 줄이 전부다.**

모르는 장치 종류는 **예외를 던진다.** 조용히 건너뛰면 레벨 데이터와 다른 월드가 만들어지고,
솔버는 그 월드를 근거로 "풀린다"고 판정한다.

**장치는 콜라이더를 가져도 된다.** `Create` 가 격리 씬과 바디 목록을 함께 받는 이유가 그것이다 —
장애물·문처럼 물리적 실체가 있는 장치는 바디가 있어야 성립한다. 폭탄이 안 만드는 것은
영역 효과 장치라서이지 장치 일반의 규칙이 아니다. 만든 바디는 `bodies` 에 생성 순서대로 넣으며,
그 자리가 `WorldBuilder` 고정 순서의 "장치" 구간(지형 뒤·스트로크 앞)이다.

`Build` 의 `injectedLogics` 주입 인자는 **제거했다.** 장치가 레벨 데이터에서 나오게 되었으므로
같은 일을 하는 경로가 둘일 이유가 없고, 테스트도 실제 경로를 타는 편이 낫다.

마찰·감쇠 설정에 달린 물리 품질 문제이고 장치 경로의 정당성과 무관하다.
