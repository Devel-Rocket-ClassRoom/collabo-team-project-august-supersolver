## 왜

**하나. 초록불이 초록불이 아닐 수 있다.**

2026-07-31 실행 리포트에서 26개 중 17개가 `InvalidOperationException`으로 죽었다.
원인은 하나였다 — `SceneManager.CreateScene`이 런타임 전용이라 EditMode에서 월드가 서지 않았다.
그런데 항목 단위로만 보면 "계약 테스트 통과", "소스 가드 통과"처럼 읽혀서
**결정론이 하나도 검증되지 않은 상태를 부분 성공으로 오독할 여지**가 있었다.

테스트가 이제 EditMode/PlayMode 두 어셈블리로 나뉘었으므로 이 위험은 더 커졌다.
결정론·판정·프레임 독립성은 전부 PlayMode에 있다. **EditMode만 돌린 리포트는 아무것도 증명하지 않는다.**

**둘. 리뷰 이력이 평가 항목이다.**

미션 요구에 형상관리와 코드 리뷰 이력이 들어 있는데, 저장소에 `.github/`가 없다.
"코어 변경 시 결정론 테스트 재실행 + 리뷰 승인"이 CLAUDE.md 본문에만 있고 절차에는 없는 상태다.
문서에만 있는 규칙은 바쁠 때 가장 먼저 건너뛴다.

## 할 일

### 1. 실행 결과 제출 형식 고정

`Docs/TestResults/`에 EditMode·PlayMode **양쪽** XML을 커밋한다. 파일명에 플랫폼을 넣어 구분한다.

판정 문서에 적을 최소 형식:

```
EditMode  : 9/9 통과 (실패 0)   TestResults/EditMode_20260801.xml
PlayMode  : 18/18 통과 (실패 0) TestResults/PlayMode_20260801.xml
```

**통과 개수만 적지 않는다.** 총 개수와 실패 수가 함께 있어야
"예외로 죽은 테스트"와 "없는 테스트"가 구분된다.

두 번 호출이 필요하다 (`-runTests`는 호출당 플랫폼 하나):

```
-testPlatform EditMode  → Docs/TestResults/EditMode_<날짜>.xml
-testPlatform PlayMode  → Docs/TestResults/PlayMode_<날짜>.xml
```

### 2. ~~`UnityEditor` 금지 토큰 추가~~ — 하지 않기로 결정 (2026-08-01)

`SimWorld.Dispose()`의 에디터 분기를 제거한 결과 코어의 `UnityEditor` 참조는 현재 0건이지만,
**이것을 자동 검사로 강제하지 않는다.** 코어에 에디터 전용 디버깅 도구(기즈모, 인스펙터 표시)를
붙일 여지를 남긴다.

결정론 금지 API와는 성격이 다르다는 점도 근거다 — `Time.deltaTime` 한 줄은 결과를 바꾸지만
`UnityEditor` 참조는 계층 위반이지 재현성 위반이 아니다. 계층은 리뷰에서 본다.

### 3. PR 템플릿 — 완료 (2026-08-02)

`.github/pull_request_template.md` 생성.

**원안은 코어 담당 관점으로만 쓰였다.** 팀 4명 중 셋은 코어를 안 건드리는데,
그들의 PR 에서는 항목이 전부 "해당 없음"만 남는다. 그러면 아무도 안 읽게 되고
정작 필요한 PR 에서도 형식적으로 체크만 하고 넘어간다. 그래서 **역할별 블록**으로 다시 짰다.

| 블록 | 대상 | 핵심 항목 |
|---|---|---|
| 공통 | 전원 | 무엇을 바꿨나 · 테스트 총계 (에셋만 바꿨으면 "해당 없음") |
| 화면이 바뀌었다면 | D · B | 스크린샷 · **세로 모드 한 손 조작** · 시뮬 중 그리기 잠금 |
| 레벨을 추가·수정했다면 | C | **빈 솔루션으로 `Clear` 가 나오는지** · 좌표가 JSON 에 있는지 · 리스트 순서 |
| 코어를 건드렸다면 | 본인 | 계약 사전 공유 · 금지 API · `Step()` 밖 물리 · 리스트 순서 |

**"해당하는 것만 남기고 나머지는 지운다"** 를 명시했다. 세 블록을 다 채우게 하면 원안과 같은 실패를 반복한다.

블록별로 넣은 것의 근거:

- **세로 모드 한 손 조작** — 기술 스택에 못박힌 제약이다. 데스크톱 에디터에서만 보면 엄지가 안 닿는 UI 가 나온다
- **빈 솔루션 `Clear` 검사** — 설계서의 솔버 0단계와 같은 검사다. 안 그려도 풀리는 레벨은 퍼즐이 아니라 반려 대상인데, 이걸 PR 단계에서 걸러야 솔버가 헛돌지 않는다
- **리스트 순서** — 원안 4개에 더한 항목. `Terrain` · `Devices` · `Strokes` · `Pivots` 의 순서가 곧 물리 등록 순서인데 **이것만 자동 검사가 없다.** 바꿔도 컴파일되고 테스트도 통과하지만 결과가 달라지고 저장된 리플레이가 깨진다. 여기서는 체크박스가 유일한 방어선이다
- **UI 작업에도 PlayMode 를 요구하는 이유** — `Assembly-CSharp` 에 컴파일 에러가 하나만 있어도 플레이 모드 진입이 막혀 PlayMode 테스트가 통째로 안 돈다. UI 담당이 스크립트를 깨뜨렸을 때 이걸로 잡힌다

임시 저장소지만 여기서 만들었다. 실제 저장소가 생기면 `.github/` 를 파일째 옮기면 되고,
"실제 저장소로 이월" 방식은 잊힐 위험이 있어 기각했다.

`.github/pull_request_template.md`. 코어 변경 시 확인 항목을 체크박스로 둔다.

- 결정론 테스트 재실행 결과 (EditMode·PlayMode 양쪽, 총/통과/실패)
- 계약 타입(`Stroke`/`Solution`/`PivotJoint`/`SimResult`/`IStepLogic`/`LevelData`) 변경 여부 — 변경 시 영향받는 팀원에게 사전 공유했는가

템플릿은 **코어 담당만이 아니라 팀 전원이 쓴다.** 항목이 길면 아무도 안 읽으므로 위 4개 정도로 끊는다.
